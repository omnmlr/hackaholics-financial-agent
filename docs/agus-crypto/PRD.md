# AGUS Crypto Product Requirements Document

**23 November 2026 · Final specification for founder review · Hackathon delivery 29 November 2026 UTC**

## 1. Product vision and success

AGUS is an Android-first, Solana-focused AI financial operating system for people who manage multiple independently owned cryptocurrency wallets. See one portfolio, understand what moved and why, choose the wallet that should pay, approve with the authority that owns the funds, and return to a verified result. Monitoring keeps the product useful between transactions. Design for active self-custody users who keep spending, trading or savings in different wallets. Creators and teams can use the same product and opt into additional tools as needed.

- **P0 Portfolio.** Unified and per-wallet balances, assets, activity and coverage.
- **P0 Intelligence.** Evidence-backed conversation that can move from a question to a reviewable action.
- **P0 Execution.** Real user-authorized transfers from connected wallets. Supported swaps use the same review and settlement model and have a separate live release gate.
- **P0 Monitoring.** Opt-in activity alerts and practical financial insights with links to the underlying evidence.
- **Optional Pocket.** A separately funded Swig account with scoped spending and a root-controlled exit. Activation is voluntary. Funding uses a linked wallet's approval. Ordinary spending aims for in-app signing after independent Android verification.
- **Supporting tools.** Payment requests, QR codes, invoices and verified receipts. Place requests and invoices in secondary navigation. The core journey must pass with both Pocket and invoicing disabled.

Wallet apps already sign, portfolio apps already aggregate and alert, and chat products already trade. AGUS should prove the combined workflow across independently held accounts. One handset demonstration should trace a wallet-attributed event, explain its effect, execute from the chosen existing signer, and find the resulting evidence in activity. Track correct answers with traceable sources, time to understand a balance change, approval and unlock counts, verified completion by wallet/provider, alert duplication and subsequent return to the app. The Android app is the financial product. The website presents the product, explains custody and distributes an authentic build when available. [Product differentiation and competitive evidence](https://github.com/omnmlr/hackaholics-financial-agent/blob/05fde1ddb55774704f32fa765c93b2fba69f304d/docs/agus-crypto/pre-prd/PRODUCT_DIFFERENTIATION.md)

## 4. Detailed functional requirements

**F1 · Wallet registry and scope.** Canonical wallet identity is cluster plus owner public address within the user registry. Distinguish linked-owned, self-designated watches, third-party watches and Pocket. Verify signed, expiring, single-use association proof bound to AGUS user, domain, session, cluster and exact wallet address for ownership/signing scope. Keep multiple provider routes without duplicating portfolio value. Watch addresses are read-only. Use verified owned endpoints for internal attribution. Unlinking removes that route's eligibility immediately, preserves authorized historical activity and leaves in-flight reconciliation available. Clear device grants and attempt wallet deauthorization where the vendor supports it.

**F2 · Portfolio and activity.** Use cluster, mint and token program as asset identity, and exact atomic units throughout. Support SOL and one allowlisted classic SPL mint for the hackathon. Prefer Circle's verified Devnet test USDC mint `4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU` if available, otherwise explicitly name the synthetic mint. Devnet units have no real USD value. Mainnet watch reads and any price estimates carry separate network, source and freshness. Show priced subtotal with coverage and unpriced holdings, never infer prices from a ticker. Merge duplicate owner/ATA observations using stable transaction and instruction leg IDs. Separate fees, rent and swap legs from transfers. Preserve both owned sides, omit internal movements from external income/outflows, and count attributable SOL fees once. Label unavailable historical token accounts, slots and lookback with per-wallet coverage. For post-hackathon Token-2022 and protocol positions, validate extension/adapter support and suppress double counting of receipt tokens. Defer historical PnL.

**F3 · Financial intelligence.** Ground combined/per-wallet balances, bounded period changes, receipts/spending, an identified transaction and source-wallet eligibility in deterministic tools. Return the snapshot ID or event IDs, time bounds and timezone, affected wallets, cluster and coverage. Ask for a missing amount, destination, wallet or date scope rather than filling it. Incomplete reads yield an observed subtotal or an unavailable answer. Keep typed drafts, approval and chain state separate from model narration. Store minimum scoped conversation context. Treat on-chain metadata, documents and prompt input as untrusted. For the prototype use server-side paid-provider credentials, an atomic configurable per-user daily allowance, small per-user concurrency and per-turn token/tool/retry caps, and a global cutoff. Deterministic reads, manual review, verification and recovery remain available when chat is throttled or its provider is down. Voice, attachments, advanced memory and periodic financial analysis are roadmap items.

**F4 · Existing-wallet transfers.** Start an identical draft from a form or chat suggestion. Validate active wallet/provider/account/cluster, exact SOL or supported mint and decimals, destination authority, balance, fee buffer, program set and possible recipient ATA rent. For classic SPL verify source and recipient account ownership and mint. Show human-readable amounts, exact accounts, fee payer, estimated fees/rent and expiry. Simulate the actual reviewed bytes. Approval binds a single revision and selected route. Use the shared lifecycle in §5.

**F5 · Supported swaps.** Start with one pinned Jupiter adapter and allowlisted pair/program set if compatible liquidity exists on the selected, explicitly labeled cluster. Quote exact input, expected output, minimum output, price impact, fees, slippage and expiry. Bind wallet, quote version, accounts, program IDs and resolved address tables to the review. Reject unknown or unaccounted instructions, unsupported address table/version, expired quote, changed order or unsuccessful simulation. Review any refresh and require a new approval. Verify final actual input/output and minimum receive, including token deltas, wrap/rent and fees separately. Keep Devnet transfer and any separately accepted swap network clearly isolated. No mainnet transaction path ships on the strength of Devnet acceptance.

**F6 · Proactive monitoring.** Server-side worker consumes finalized observed events independent of device state. Start with one opted-in external inflow rule, threshold optional by asset, and one in-app inbox. Evaluate by canonical event and matching wallet. Store a unique rule/event/wallet key, advance cursors after durable writes, and recover after missed runs. Alert details show matched evidence and timestamps. Partial or stale coverage is visible. Post-hackathon add spending summaries, configurable outflow/budget rules, push/digests and privacy controls for notification previews. Monitoring has read-only access and suggestions enter the normal draft flow.

**F7 · AGUS Pocket.** Optional direct Swig integration, one account per user/cluster in the pilot. Creation uses a user-held external root. Deposit, bounded signing, role administration and recovery follow §6. Keep every Pocket capability gated by verified program, authority and signed-device evidence.

**F8 · Requests, QR, invoices and receipts.** From an owned eligible receive wallet or enabled Pocket, create a Solana Pay request with network, exact mint/SOL, amount, recipient and unique opaque reference. Generate a payment URI and a network-labeled share view. Use a share-link QR on Devnet because a standard transfer URI leaves cluster selection to the wallet. A simple optional invoice adds title, off-chain notes and optional due date. Keep off-chain metadata out of the chain payload. Display open, cancelled, expired, needs review and settled status. Match only successful finalized correct-chain evidence for the exact recipient account/authority, mint and amount with an unambiguous reference. Exceptions, partial/overpayments or multiple candidates require review. Deduplicate observations and settlement. Provide verified outgoing receipts from the common execution journal even when requests and invoicing are disabled. A QR, signature string, invoice upload or paid claim is a lookup hint.

## 5. Existing-wallet signing and settlement

1. **Select and review.** Bind the authenticated actor, cluster/genesis, source address, provider route, operation/revision, decoded instructions, exact message digest, expected accounts and effects, simulation slot, blockhash and expiry. A change of route or transaction terms invalidates approval. Persist the draft and a durable attempt/claim before opening a wallet.
2. **Authorize and hand off.** Android selects the intended package or uniquely supported vendor association. Reauthorize the per-provider/account/cluster credential from SecureStore and independently check the returned address and capabilities. Use MWA 3.0.2 as the reviewed starting point. Keep the package-specific bridge small and auditable. Show identity warnings, wallet cancellation, power restrictions and missing capabilities. Never bypass vendor attestation or silently route to a different wallet. Vendor deep links require distinct acceptance and authenticated callback correlation.
3. **Submit exactly the reviewed message.** Baseline sign-only can return signed bytes for server verification and a single submission claim. For a tested MWA sign-and-send route, AGUS persists the operation's signature or independently searchable reference and waits for an independent chain read. Keep one selected path per attempt. Guard app resume and duplicate taps with the same attempt. A lost response yields `unknown` with continued reconciliation.
4. **Verify, reconcile and recover.** Check pinned RPC genesis, transaction message bytes/digest, expected signers, `meta.err`, finality, fee and decoded asset/account/amount effects. Check the known signature first, otherwise the bound reference plus scoped history and exact content. Confirmed/pending may update the state before finalization. Issue a receipt only after successful finalized verification. A definitive failure or an expired blockhash with adequate independent history permits a fresh review. Incomplete or conflicting evidence leaves the attempt unresolved. Do not instruct a replacement or autobroadcast on app restart. Surface Verify status, decline/reconnect and an explicit new review when eligible.

Persist the state transitions and correlation IDs. Keep raw signed bytes only where a sign-only submission needs them and apply an explicit restricted retention policy. Log digests and identifiers for review, avoid secrets and raw signed payloads in logs. Separate deployable secrets and mobile credentials. Require verified app association, release signing, proven cold/warm return, and a live capability flag per cluster, vendor and operation.

| Phase | Product and engineering requirement |

## 7. Service architecture and data

Extend the existing modular application and worker. Keep financial rules in reusable service modules that both HTTP endpoints and agent tools call. Use Postgres for durable and user-scoped records. Use RPC for canonical chain reads and settlement, with a configurable independently operated read endpoint or indexer for coverage or corroboration. Pin expected genesis hash, commitment, endpoints, supported programs and mint metadata per deployment. Never mix test/mainnet identities or prices. The web site holds no signer or financial session. Android keeps the wallet bridge and device credentials outside the generated HTTP client.

| Service | Persistent records and boundaries |
| --- | --- |
| Identity and wallet registry | Existing AGUS user/session. `wallet` keyed by user, cluster and address, with attribution and ownership proof time. `wallet_route` has public provider/capability/status metadata keyed by wallet and provider. Challenge stores digest, scope, expiry and consumption. Secrets and native grants stay off the server. |
| Portfolio, activity and prices | Normalized asset registry keyed by cluster, token program and mint or native SOL. Balance snapshots and holdings by wallet/token account, adapter-position identity and coverage observations, timestamped price and source. Canonical chain transactions keyed by cluster/signature. Events keyed by cluster/signature/outer-inner instruction and leg index. Wallet-event edges preserve attribution. Confirmed slot, block time and observation time are separate. |
| Action and settlement | Reuse draft/audit stores. Persist immutable review revisions and approval, transaction attempts with unique operation/active claim, signature/reference lookups, monotonic state transitions, and final receipt keyed by cluster/signature and bound attempt. Use transaction boundaries or compare-and-swap for claims and finalization. Keep older drafts readable and deny new signing on incomplete historical review state. |
| Agent | Existing model adapter and tool runner with user scope, typed input/output and optional usage counters keyed by identity and day. Conversations and evidence are private to that identity. Log tool timing and correlation with redacted payloads. |
| Indexer, alert worker and finance tools | Durable per-cluster/address cursor and observation window, bounded backfill, retries with jitter and overlapping checkpoints. Alert rule and inbox entry with deduplication constraint. Reuse payment requests, reference registry, request evidence and settlement APIs. Advancing cursors and writing derived work must be atomic or replay-safe. |
| Swig Pocket | Root, configuration/vault addresses, validated program identity, roles, cap/expiry observation and pending transitions. On-chain authority, balance and finalized actions are authoritative. Store only public role identifiers and signer metadata server-side. |

Each permission or data plane uses authenticated user scope and least privilege. External addresses are public but wallet grouping, chat, preferences and invoices are private. Apply HTTPS, release-only verified callbacks linked to the operation, session expiration/revocation, same-origin checks as applicable, structured input validation and bounded pagination. Treat name resolution, QR content, models and vendor quotes as untrusted. Display the resolved address for review. Use append-only security events for approvals, signature claims, finalized receipts and revocations. Prevent reporting one user's resource IDs or financial history to another user. Put provider credentials in the existing server configuration and store release signing credentials privately.

## 8. Performance, reliability and measurement

These are prototype acceptance targets for a midrange physical ARM64 Android handset, Wi-Fi or ordinary 4G, two linked wallets plus one watch, and a bounded seven-day activity window. Record device, network and API versions. Measure at least 20 warm UX/read samples where practical. Capture cold and wallet-return traces separately. Chain finality, external wallet interactions and provider limits are reported separately from AGUS processing time.

| Area | Target and behavior under degradation |
| --- | --- |
| Launch and navigation | p95 interactive portfolio within 2.5 s cold with cached data after session restoration, or an actionable signed-out/loading view. Show route/tap feedback within 150 ms and preserve scroll and scope across tab or wallet return. Initial live refresh starts immediately and times out with a visible retry. |
| Reads | p95 cached portfolio/activity API within 750 ms, first page at most 25 events, initial live or explicit partial response within 5 s. Show update timestamps. Mark balance snapshots stale after 2 min in live demo and optional prices after 15 min. Never replace valid cached balance with a zero on provider failure. |
| Conversation | Show a progress state immediately. p95 complete answer within 10 s for supported bounded questions with healthy dependencies, hard cap 15 s before explaining degradation and offering directly browsable evidence. Never retry model-triggered financial effects. |
| Handoff and settlement | Show persisted attempt within 1 s of app return after local state loads. Refresh pending status on resume and via server worker, back off on RPC throttle, and aim to show a verified receipt within 15 s of finality becoming observable. Unknown stays recoverable across restarts. Retries deliver at most one logical receipt and alert per unique event. |
| Monitoring and health | p95 inbox delivery within 90 s of a qualifying finalized event being observed under normal service, with 30 s worker cadence target and a visible last-check time. Log queue lag, missed coverage, stale read rate, provider errors, reconciliation age, duplicate suppression and AI usage. Gate release on healthy worker and RPC, zero venue/cluster routing errors and no unresolved critical safety defect. |

## 12. Hackathon scope, rubric and roadmap

**Hackathon core.** Solana-only. Devnet sends and verification, SOL plus one allowed classic SPL mint, two distinct owned wallet views, scoped watches, bounded history/coverage, grounded text, deterministic source choice and one real in-app alert.
