# Capability and limitation matrix

The table describes authority over existing accounts unless a row names a new account. “Can sign” means the correct authority can sign a supported transaction under that row's policy. It says nothing about a particular wallet version's UI or a downstream program accepting the transaction. See [authorization sources](existing-wallet-authorization.md), [implementation evidence](competitor-architectures.md) and the [executed delegation proof of concept](existing-wallet-delegation-poc.md).

## Android, security, cost and scalability

| Approach | Android usability | Trust and enforcement | Incremental cost drivers | Scale constraints |
| --- | --- | --- | --- | --- |
| RPC/indexing | Fast in-app reads. No signing handoff. | Public ownership data, RPC availability and indexer integrity. Cross-wallet grouping is sensitive user data. | RPC capacity, indexer, metadata and pricing. | Batch by cluster and source address. Cache shared mint/price metadata and bound history backfills. |
| External wallet signing | Package/account selection, wallet launch, possible unlock and callback per action. Warm wallets and saved grants may reduce friction. | External wallet holds the key. Validate app identity, account, cluster and exact bytes. Send results can be ambiguous until verified. | Network fees, optional priority fee, and recipient ATA rent when needed. MWA itself is an open protocol. | Human approval latency dominates. Serialize wallet handoffs per device and settle independently. |
| Phantom Auto-Confirm | Shorter flow for eligible apps, still subject to wallet policy and version. | Wallet-managed authorization and security checks. Published feature specifies time and rate limits. | Usual network fees. | Ten transactions per minute for up to two hours according to Phantom support. Eligibility and whether AGUS can use the feature are open. |
| Ordinary delegate | Owner wallet approval for setup or revocation. Later pulls can happen without a mobile handoff. | Token program enforces amount. Delegate operator controls the destination within protocol rules and could burn allowance. The source account's existing delegate may be displaced. | Grant, revoke and pull fees. Possible recipient ATA rent and signer/scheduler infrastructure. | One delegate per token account. Parallel spends against one source contend for writable account locks. |
| Foundation Subscriptions | Owner approves setup in the external wallet. Subsequent pulls are off-device. A max token approval requires clear disclosure. | On-chain terms enforced through the program. Adds program upgrade, audit and puller trust. Insufficient funds roll back a pull. Another approval replaces the PDA and blocks pulls, while grant records may survive. | README reference rent is 0.00162864 SOL for authority plus 0.00235944 SOL for a recurring grant, about 0.00398808 SOL together before fees and ATA rent. Check live rent parameters for planning. Recurring pulls and indexer/worker operations are additional. | Several grants share the same delegate slot and source balance. State accounts, recurring writes, payer funding and index/reconciliation scale with active grants. |
| Swig | Root approves opt-in setup and funding. Later operations can run through a scoped signer. User needs a visible exit path and separate balance. | Program enforces exact role actions. Trust includes deployment/upgrade and signer isolation. Program and destination scope require testing. | Config and token-account rent, creation/funding and role-change fees, CPI compute and priority fees, and optional paymaster costs. | Parallelism follows wallet/state account ownership. Batch size is constrained by signatures, accounts, compute, CPI and writable-state contention. |
| Privy | Embedded signing can reduce app switches for its own wallet. External routes retain wallet handoffs. | Privy authorization, enclave signing, policy semantics and service availability join the trust boundary. | Provider plan, usage metrics, signing and transaction volume, plus network fees or sponsoring. | Service quotas and usage-priced throughput plus ordinary Solana contention and worker reliability. |

Solana documents a base transaction fee of 5,000 lamports per signature and optional prioritization. Multiple signatures, account funding and retry attempts can change total cost. Subscription deposits follow the program's account lifecycle and refund rules. A quote should distinguish signature fees, priority fees, rent deposits and provider charges. The local experiment measured rent under its own runtime configuration. [Solana fees](https://solana.com/docs/core/fees) · [Rent RPC](https://solana.com/docs/rpc/http/getminimumbalanceforrentexemption) · [Subscriptions rent examples](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/README.md#rent-costs) · [Swig pricing](https://onswig.com/pricing) · [Privy pricing](https://www.privy.io/pricing)

For independently owned wallets, AGUS should prepare and reconcile child transactions separately. A single Solana transaction can require several signers and commit atomically, but collecting compatible partial signatures across mobile wallets on the same unmodified message before its blockhash expires is a separate integration project. Independent sends can partially complete, even when prepared from a single conversation.
