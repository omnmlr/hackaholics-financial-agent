# Existing-wallet authorization on Solana

## Public reads, wallet connections and approvals

A public Solana address is enough to read native balance, owned token accounts and available transaction history. Linking is useful for identifying an approved signing route and can separately prove address control through a signed challenge. A signed login challenge gives AGUS no transaction authority. Index SOL, classic SPL and Token-2022 separately. Track protocol positions through protocol-specific decoders or indexers where coverage is available. [Solana token-account RPC](https://solana.com/docs/rpc/http/gettokenaccountsbyowner) · [Wallet Standard](https://github.com/anza-xyz/wallet-standard) · [Sign-in with Solana](https://docs.phantom.com/recipes/auth/sign-in-with-solana)

**MWA (documented).** Open a short wallet association and call `authorize` for the chain, app identity and requested addresses. The wallet returns authorized accounts, an opaque `auth_token` and optionally `wallet_uri_base` for future connections. Use the token with the issuing wallet and authorized chain. It can streamline connection approval, and the wallet can rotate it, change the returned accounts or reject it. Re-check the exact address on every handoff. `deauthorize` invalidates the token at the wallet; deleting local state only unlinks locally. Query supported capabilities and transaction versions. Prefer `signAndSendTransactions` for ordinary MWA payments when available. Sign-only is optional and deprecated in the current feature list. The wallet owns the signing decision and may request approval, unlock or account selection. The spec describes silent *reauthorization* and permits the wallet to decide when a transaction prompt applies. A batch still consists of individual transactions and can partially submit. [MWA specification](https://github.com/solana-mobile/mobile-wallet-adapter/blob/main/spec/spec.md#privileged-methods) · [React Native sessions](https://docs.solanamobile.com/get-started/react-native/invoke-mwa-sessions-directly)

**Platform and wallet differences.** Solana Mobile lists native Android and Android Chrome as supported MWA environments. Its current compatible-wallet directory lists Solflare and Backpack. Phantom's Android MWA connection was observed in the AGUS journal and requires independent signing acceptance. Desktop web can use Wallet Standard discovery. iOS requires a separate transport such as a documented vendor link. Seeker Connect targets the certified device wallet through a separate integration. [Solana Mobile platforms](https://docs.solanamobile.com/developers/mobile-wallet-adapter) · [Wallet directory](https://wallets.solanamobile.com/) · [AGUS device journal](https://github.com/omnmlr/hackaholics-financial-agent/blob/87be10e5e9f4606e0c902f67f488a9c8f1823869/docs/agus-crypto/PROGRESS.md) · [Seeker Connect](https://github.com/solana-mobile/seeker-connect)

## Classic SPL and Token-2022 account delegates

**Documented.** The token-account owner signs `Approve` or `ApproveChecked` for one source token account and raw allowance. `ApproveChecked` verifies mint and decimals. One account has one active ordinary delegate and reapproval replaces its authorization. The delegate can transfer or burn from that account up to the remaining amount with its own signature. The owner keeps direct control, can spend the balance independently and can sign `Revoke`. Unspent allowance can reach future deposits. The token program does not encode a payee, calendar, expiry, reset, multi-delegate policy or general transaction signing right in that allowance. Granting the allowance and each later delegated transfer are transactions with a fee payer. [Approve delegate](https://solana.com/docs/tokens/basics/approve-delegate) · [Revoke delegate](https://solana.com/docs/tokens/basics/revoke-delegate) · [Solana spend permissions](https://solana.com/docs/payments/advanced-payments/spend-permissions)

**Asset boundary.** Native SOL in an ordinary System Program account requires that account's signing authority for an outgoing transfer. It has no SPL delegate field. Wrapped SOL (WSOL) is a balance in a native-mint token account. Wrapping and funding it is a separate user action and changes where the SOL is held. A delegate can only exercise supported token operations over that account. Closing and unwrapping require the appropriate close authority. A token delegate can satisfy a downstream program only where that program and route explicitly support the delegated signer and source. Typical wallet-owned swaps, staking and DeFi can require owner or position authority, account creation, and extra program calls. [System Program](https://solana.com/docs/core/programs/builtin-programs) · [Wrapped SOL](https://solana.com/docs/tokens/basics/sync-native) · [Jupiter swap transaction building](https://developers.jup.ag/docs/swap/build)

**Token-2022.** Ordinary account delegation is available under Token-2022. Eligibility must include the token program ID and mint/account extensions. Transfer fees alter debit and net receipt, transfer hooks add required accounts and program execution, and restrictions such as frozen accounts, non-transferability, required incoming memos and CPI Guard can affect delegated flows. Track actual execution semantics per extension set. Permanent Delegate is a mint-level authority configured by the mint issuer, with power over token accounts for that mint. It is separate from a user-approved account delegate and a holder cannot revoke it through the ordinary account revoke instruction. [Token-2022 extensions](https://www.solana-program.com/docs/token-2022/extensions) · [Permanent Delegate](https://solana.com/docs/tokens/extensions/permanent-delegate)

## Solana Foundation Subscriptions

**Implemented.** A Subscription Authority PDA for each user and mint occupies the single existing delegate slot on the user's canonical ATA with a `u64::MAX` raw allowance. The program gates transfers through individual delegation or subscription PDAs. The source ATA remains under the user's ownership and funds stay there until pulled. The user approves initialization and the desired permission or plan on-chain. A fee sponsor can pay fees and eligible account rent without taking the owner's approval role. Calls require a transaction from an authorized puller, scheduler or submitting program as appropriate. Nothing executes solely because the clock advanced. [Pinned README](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/README.md) · [Authority initialization](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/program/src/instructions/initialize_subscription_authority.rs)

- **Fixed and recurring grants.** Fixed grants have a remaining total amount and optional expiry. Recurring grants enforce a per-period allowance, period length and configurable end. Check recipient semantics before use. At the reviewed revision the ordinary fixed and recurring handlers do not bind the receiving owner to a stored payee. A programmatically capped delegate can still choose where to direct the permitted amount. [Fixed handler](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/program/src/instructions/transfer_fixed_delegation.rs) · [Recurring handler](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/program/src/instructions/transfer_recurring_delegation.rs)
- **Subscription plans.** A merchant publishes terms. A subscriber accepts them and approved pullers collect within the plan's billing rules. The plan handler checks the destination owner against the plan's allowed destinations. Validate who can change these destinations or pullers and which terms are pinned on signup before treating a plan as a recipient restriction. [Plan transfer handler](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/program/src/instructions/transfer_subscription.rs) · [Program release](https://github.com/solana-foundation/subscriptions/releases/tag/program-v0.5.0)
- **Lifecycle and trust.** The source may be spent, frozen or have its delegate replaced, causing a pull to fail even while an application-visible subscription is active. The owner can revoke the ATA delegate and use the program's cancellation or authority teardown path as appropriate. Cancellation at period end and immediate cancellation have different semantics. The upstream docs also distinguish authority teardown from simple delegate revocation for rent reclamation and describe lifecycle constraints when setup transactions remain valid but unsubmitted. Favor short-lived, immediately submitted grant transactions. The repository declares program `De1egAFMkMWZSN5rYXRj9CAdheBamobVNubTsi9avR44` and describes Squads-governed upgrades. Confirm the target deployment, actual upgrade authority and audited commit versus deployed bytes before relying on a max approval to this program. [Security considerations](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/README.md#security-considerations) · [Audit status](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/audits/AUDIT_STATUS.md) · [Upgrade mechanism](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/docs/004-program-upgrade-mechanism.md)
- **Asset scope.** The program supports classic SPL and Token-2022 pulls. At the reviewed revision its transfer path accepts caller-supplied transfer-hook accounts and does not support destinations requiring an incoming memo. Confirm each extension combination and version. The program documents token pulls, with no general native SOL, swap or DeFi authority. [Token support and demo](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/README.md)

## Optional Swig smart account

**Documented and implemented upstream.** Swig separates a configuration account storing roles from the wallet address that owns assets and signs through the program. The user's existing wallet can act as root for account creation, role grants, rotation and revocation. Session authorities can sign within their role until slot-based expiry or removal. The program exposes SOL and token budgets, recurring slot windows, destinations, program permissions and staking permissions. The root or relevant authority signs role/session changes. A worker signs and submits later authorized operations. A role budget alone cannot stand in for validating program access and actual instruction effects. For a routed swap, check CPI behavior, the participating programs, asset changes, route compatibility and the role's exact permissions. [Swig program](https://github.com/anagrambuild/swig-wallet/tree/c64127837995818ef5d1e161bbc367391a1b5765) · [Sessions](https://build.onswig.com/solana/authorities/sessions.md) · [Spending limits](https://build.onswig.com/solana/permissions/spending-limits.md) · [Program access](https://build.onswig.com/solana/permissions/program-access.md) · [Swaps](https://build.onswig.com/solana/use-cases/swaps.md)

Normal Swig execution uses assets held at the Swig address or designated sub-account. Users explicitly fund only the amounts they want to automate. As a separate candidate, a compatible Swig PDA could be authorized as a delegate over an existing token account, subject to token-delegate limits and integration tests. The Subscriptions repository includes smart-wallet compatibility tests for program-controlled authorities. That result supplies no native SOL rights over any external account. [Subscriptions wallet compatibility](https://github.com/solana-foundation/subscriptions/blob/efb735d01ac46e8240864c9e3fc603d2341714da/README.md#smart-wallet-support)

## Optional Privy embedded wallet

**Documented.** Privy supports authenticating and linking external wallets and documents mobile deep-link connectors for Phantom and Backpack plus a generic connector. External signing is still mediated by the external wallet. Separately, an owner of a Privy-managed wallet can add or remove additional signers, including server authorization keys or quorums, with signer-specific policies. The server can then request allowed signatures via Privy's enclave-based signing infrastructure. Privy documents offline and recurring uses such as limit orders and rebalancing. An AGUS worker would still schedule, submit and reconcile operations. Check policies against actual Solana instructions, including account and program constraints. [External wallet authentication](https://docs.privy.io/authentication/user-authentication/login-methods/wallet.md) · [Expo external-wallet links](https://docs.privy.io/recipes/react-native/deeplinking-wallets.md) · [Additional signers](https://docs.privy.io/wallets/using-wallets/signers/overview.md) · [Add signers](https://docs.privy.io/wallets/using-wallets/signers/add-signers.md) · [Solana policy examples](https://docs.privy.io/controls/policies/example-policies/solana.md)

This provides an optional embedded account and a hosted signing trust model. Assets at an independently owned external address stay external when linked. Privy's additional-signer permissions apply to the wallet provisioned within its infrastructure. Revoke by removing the signer in Privy and verify how outstanding signed messages are handled. The service's signing policy and availability are separate dependencies from Solana confirmation.
