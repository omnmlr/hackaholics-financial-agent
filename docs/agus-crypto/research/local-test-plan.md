# Proposed next-stage test plan

Run these experiments separately from the product and the research PR. Use a pinned LiteSVM or local validator, fixture programs, synthetic balances, ephemeral test signers and stub price/indexer services. Configure the harness for its local ledger and reject public RPC or real-wallet credentials. Preserve chain and wallet transport fixtures separately so that simulator success cannot be mistaken for Android device acceptance.

Record the code commit, dependency versions, program ID and binary digest, test network, fixtures, signer roles, expected and actual balances or errors, compute units, fees and rent. Record local transaction identifiers as local evidence. Report tested instruction paths and configurations individually. Keep session tokens and signer material out of reports.

| Priority and experiment | Cases and pass criteria | Evidence produced |
| --- | --- | --- |
| **P0 — Core Android signing contract** | Use stub MWA clients for Phantom, Solflare and Backpack in a package/account/chain matrix. Validate connect, multiple returned accounts, Phantom → Solflare → Phantom, cold restart, rotated/expired grants, wallet deauthorization and watch-only addresses. Exercise valid and invalid app identity metadata, blocked wallet/device capability, cancellation and returned account changes. Every wrong wallet, account or chain must stop before a signing request. Each success must use the exact reviewed transaction. Mock the UI prompts as outcomes, with their physical behavior left open. | Per-route and per-account results, callback fixtures, approval count in the stub, and comparison with PR #46 evidence. |
| **P0 — Local transfer and settlement** | Run native SOL and one classic SPL transfer from each of two independent synthetic owners. Test existing and newly created recipient ATAs, exact decimals, same owner across providers, insufficient fees/rent and holdings outside the source ATA. Test stale blockhashes, mismatched returned bytes, finalized execution errors, dropped callbacks, delayed confirmation and simultaneous duplicate attempts. A restart must recover pending attempts and produce at most one verified settlement for a logical operation. Portfolio totals must not duplicate holdings and must expose stale or missing data. | Balance and account-state diffs, expected and finalized message comparison, fee/rent data and state transitions across restart. |
| **P1 — Ordinary token delegate baseline** | Approve a small allowance over one synthetic classic SPL and one supported Token-2022 account. Check that owner and balance are unchanged at grant time. Verify cumulative transfer allowance, burn ability in a disposable fixture, reapproval replacing the previous delegate, revocation, owner spending and future deposits. Demonstrate that native SOL balance is unaffected by the grant and confirm WSOL is a separate token-account case. Include representative Token-2022 fees, hooks and CPI or memo restrictions where supported by the fixture. | Authority fields and pre/post balances, requested versus received amount, and the boundaries where an ordinary allowance cannot meet payee, expiry or recurring requirements. |
| **P1 — Foundation Subscriptions on an existing ATA** | Pin an audited program release and test the source revision separately where behavior differs. Use one user's canonical ATA with a pre-existing delegate, then exercise initialization and user consent to max allowance, fixed grant, recurring grant and a finite merchant plan. Verify due-period checks, no implicit pull, expiry, exhausted allowance, recipient enforcement in the plan and signer authority. Use a controlled clock to show rollover and missed periods. Compare simple SPL revoke, program cancellation and authority teardown, including rent refunds and signed-but-expired setup. Verify empty/frozen/replaced-delegate outcomes, competing due jobs, actual debit versus net credit and representative Token-2022 hook and memo compatibility. The source remains user-owned and funded in place until an authorized pull. | Instruction/authority and recipient matrix, period and cancellation boundaries, one final receipt per due occurrence, unit cost and a list of exact acceptable mint configurations. |
| **P1 — Optional Swig vault** | Start with the PR #46 local baseline and a separately funded synthetic vault rooted in the user's test authority. Verify root funding/withdrawal, scoped role creation, destination checks, cumulative and recurring caps, expiry and revocation, including rejection of a pending session-signed transaction when execution follows role removal. Compare cap-only behavior with the intended explicit program configuration using harmless local fixture programs. Check which token programs and CPI paths satisfy the intended role. Root must be able to remove the delegated role and withdraw all remaining authorized assets. The external owner's native SOL must remain outside the vault policy. | Allowed-action matrix with expected rejections, role/slot and asset deltas, recovery outcomes, compute cost and fee-payer use. |
| **P2 — Swap and narrow DeFi route** | Start with a deterministic local fixture for a single wallet-approved swap. Validate exact source, resolved address lookups, mint/program IDs, output to the intended wallet, minimum output, quote age, fees and actual deltas. Compare an ordinary owner signature, a token delegate where the fixture explicitly supports it, and a Swig role with the funds at Swig. Follow with one narrowly scoped fixture position and test its explicit authority requirements. Keep venue-specific claims open until the exact downstream code and route are verified in a reproducible environment. | Per-route signer requirements, instruction/position checks, output and program effects, and unsupported cases. |
| **P3 — Privy policy contract, conditional** | Use local stubs to compare owner consent, signer addition/removal, permitted and rejected Solana requests and provider outage/retry behavior. Require external wallet routes to stay independent of Privy-managed signer policy. If embedded onboarding becomes a priority, define a separate sandbox evaluation of provider policy, recovery, quotas and sponsorship. | A contract-level comparison and list of provider-specific behavior requiring separate verification. |

## Decision gates

1. **Core local gate.** Device mocks and local execution meet the P0 assertions. No cross-account approval, unreviewed message changes or duplicate settlement across restart.
2. **In-place recurrence gate.** The exact Subscriptions version enforces the advertised amount and billing period in local tests. A payee-bound option proves its destination restriction and grant-mutability semantics. Revocation and visible failure states match the product's promises. Keep schedules on per-run approvals if the source, payee or cancellation rules fall short.
3. **Optional vault gate.** The approved Swig role passes asset, destination, program, expiry and revocation checks for its intended route. The user-controlled root can exit independently. Automated swap or DeFi requires separate evidence for each route.
4. **Android device gate, separate from local simulation.** PR #47 still requires real Phantom → Solflare → Phantom signing. First diagnose the Phantom identity warning and force-close, record the exact device/wallet versions and address the Solflare power-saver restriction separately. With a separately approved physical-device run using disposable Devnet accounts, capture cold/warm wallet launch and unlock, prompts, return time, restart and renewal, declines and three distinct finalized signatures with matching messages. Add Backpack as its own acceptance row. No physical result is implied by this plan.
