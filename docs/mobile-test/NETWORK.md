# From wallet release checks to physical mobile infrastructure

## Product and validation gates

AGUS starts with Solana Android developers who need repeatable evidence across an APK, wallet callback and actual settlement. Make that same test portable across dedicated devices before expanding to enterprise QA and comparing AI agents on realistic tasks. Enterprise buyers may value reproducible acceptance, fleet coverage and permission controls. AI teams may value scored tasks and separately licensed interaction data. Both remain unvalidated markets for AGUS.

The prototype registers and leases operator-approved ADB environments. It scores an agent's financial conclusion using deterministic evidence. Scenario execution is scripted. The score measures evidence interpretation and provides run latency and action counts. It does not measure an agent's autonomous UI policies, tool efficiency, recovery choices, downstream training benefit or relative model capability.

## Device capability and scheduling

The version 1 prototype observes Android manufacturer/model, version, available memory and storage, battery percentage and reported battery temperature for authorized environments. These are limited runner observations from this session. Virtual device observations are labeled `emulated_android`. SDK properties and battery sensors are potentially spoofable. Operator aliases and device class declarations are separate from the readings. Physical runner claims have `hardwareAttested: false`. Missing readings remain null. The emulator's battery value is synthetic and cannot inform health pricing.

For a first hardware pilot:

- Record OS/API, security patch, OEM/model family, architecture and coarse performance classes as observed values. Use a randomized fleet ID. Omit serial, IMEI, Android ID, identifiers from accounts or installed app lists. Never infer manufacturing age from software build dates. Model release dates and provider-reported age belong in declared metadata.
- Measure storage via available-byte buckets and memory via available-byte ranges. Use controlled Macrobenchmark or Perfetto tasks and stable latency quantiles, so model differences are distinguishable from initialization and thermal throttling. Collect no filesystem paths, process lists or application inventories. [Android Macrobenchmark in CI](https://developer.android.com/topic/performance/benchmarking/benchmarking-in-ci)
- Use supported BatteryManager APIs for current charge and health signals, and thermal status/headroom where exposed. Manufacturer-dependent cycle count and state of health need absent and stale values. Never silently convert charge level or battery health codes into remaining capacity. Declare sample age, OS/API support and a low-battery/thermal lease policy. [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager) · [Thermal APIs](https://developer.android.com/games/optimize/adpf/thermal)
- Probe a fixed AGUS-owned endpoint with short, low-volume traffic to measure latency, jitter, packet loss and throughput. Distinguish active measurement, provider-declared coarse country or carrier group, and simulated network shaping. Avoid SSIDs, BSSIDs, exact GPS, phone/billing data and exposed client IPs in results. Coarsen and suppress rare combinations that could identify a provider. [Android privacy changes](https://developer.android.com/about/versions/10/privacy/changes)
- Broker leases by compatibility, availability window, fresh healthy measurements, expected completion and price cap. Add fairness and capacity limits. Maintain heartbeats, lease expiry and audit logs. Reassign safely after failed allocation or checkpointed read-only work. For unknown wallet sends or irreversible app actions, reconcile same intent/evidence before allocation or payout decisions. Keep one-use grants and idempotent state transitions.
- Start with per-run fixed pricing and completed evidence requirements. Collect acceptance and retry rates by hardware class to estimate cost. Use availability only to schedule. Rare conditions may earn a premium when customers repeatedly select them and outcomes are reproducible.

## Everyday-phone isolation

| Approach | Assessment |
| --- | --- |
| Secondary Android user | Separates apps and accounts by user, with OEM variation, foreground limits and admin requirements. Shared hardware, notifications and system operations still require controls. ADB is a broad privileged debugging channel across a device. It is appropriate only for dedicated lab profiles. [AOSP multi-user](https://source.android.com/docs/devices/admin/multi-user) |
| Managed profile | Work containers offer controlled app, storage and policy boundaries. Provisioning requires a Device Policy Controller and owner cooperation. Cross-profile intents, delegated permissions, screen capture and the boundary to the personal side require verification across OEMs. Start with enterprise-owned dedicated devices, document removal and exercise negative tests. [Work profiles](https://developer.android.com/work/managed-profiles) · [Android Enterprise security](https://developer.android.com/work/dpc/security) |
| Android Virtualization Framework | Protected VMs can isolate selected workloads on supported devices. Microdroid provides a minimal Linux/Android runtime, with no general Android app UI stack. An app with OEM-native wallet and Secure Element behavior needs a different environment or an attended device. [AOSP AVF](https://source.android.com/docs/core/virtualization) |
| Restricted in-app runner | Scope automation to an owned app's test SDK or reviewed instrumentation, preferably on a clean profile. APKs and steps must be pinned and job grants time-limited. Keep transport outbound and explicit, avoid arbitrary shell, file transfer, accessibility or full screens. Play's AccessibilityService policy expressly restricts autonomous action outside verified disability tools. Design distribution without that dependency. [Play Accessibility API policy](https://support.google.com/googleplay/android-developer/answer/10964491) |

Consumer enrollment remains gated on an OEM and distribution proof. The first pilot should test app visibility, files, contacts, notifications, clipboard, cross-profile intents, wallet separation, network egress and survival after restart. Use test data and a local emergency stop that revokes the lease and blocks future actions even when the server is offline. On provider override, excessive heat, low charge, profile change or watchdog timeout, end the session and purge or reset the test profile. Capture only the approved surface and default artifact upload to zero on personal devices. Publish privacy disclosures, verify Google Play Data safety and dApp Store submission separately, and review retention and deletion. Do not install a consumer runner using today’s lab ADB control.

## Evaluation and consented trajectories

Use scenario version, app bytes, model/policy/temperature, device profile class, normalized workload and wallet/network mode as comparison keys. Randomize run order and paired tasks, separate retries from first attempts, and report denominators and timeouts. Add completion, wall time, actions, invalid or unnecessary actions, recovery choice, financial correctness and policy flags. Future resource numbers need matched device measurements and cannot be derived from one battery reading.

The current report is a private trace of steps, callbacks, evidence digests and device measurements. A training export would have a separate consent grant scoped to purpose, retention, allowed fields and parties. Export only approved synthetic screenshots, actions, projected observations, profiled environment, outcomes and provenance. Use stable event order and data-loss masks. Keep raw content and action trajectories tenant-private. Separate evaluation and training splits, avoid retaining prompts or conversations from outside the task, and audit deletion and reuse. Withholding training authorization must not block an ordinary app test.

## Receipt and settlement boundary

The implemented Ed25519 report seal binds the report, build hashes, scenario hash, environment alias, lease timestamps, outcome, artifact digests and relevant transaction signature. Verify it with a pinned runner public key. A valid signature proves who made a claim and the integrity of the included data. A trusted runner could still submit counterfeit observations. Stronger claims require attested enrollment, isolation, measurement provenance and independent sampling.

SAS manages a credential authority, schema and authorized issuers. An optional Devnet schema can state that a trusted runner signed an off-chain receipt digest for an approved scenario and cluster. Keep artifact payloads, device identifiers, wallet records and sensitive metadata off-chain. Include version, evidence class, issuer, expiry/revocation, and enough domain separation to bind the digest to AGUS. Do not assert device physics or location based on SAS, Genesis Token or the runner signature alone. [SAS source 70491fe](https://github.com/solana-foundation/solana-attestation-service/tree/70491fedf9f1247d3025a182b5785e77d4bf6be9) · [SAS documentation](https://solana.com/docs/tools/attestations/overview)

A future funded Devnet job carries immutable quote, approved Circle test mint, buyer, provider, job ID and expiry. The verifier accepts an exact finalized token transfer plus unique job binding. Use a new audited escrow or adapt the existing one after confirming its state semantics. Completion releases funds to the agreed recipient. Failure or expiry routes to refund or dispute based on terms, and unknown payments are reconciled before retry. The current local settlement uses disposable infrastructure and a local mint. Devnet read-only checks confirm the designated test mint and old SOL transaction access. Routing a real Devnet USDC payment needs a funded disposable test wallet. SKR is for ecosystem incentives and Guardians, with no dependency or earnings promise in AGUS.

Seeker Connect, MWA, Seed Vault, Genesis Token, .skr identity and the approved Devnet APK remain part of the benchmark matrix. Add a real Seeker lane with attended signing and separate provenance. Partner conversations should start with standardized pre-submission evidence and a limited benchmark pilot. AGUS has no claimed official partnership.
