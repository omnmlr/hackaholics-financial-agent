## Gate and product definition

- **Customer.** Developers and QA/release owners shipping Solana Android APKs with wallet handoffs, especially teams preparing a dApp Store release. The failure to catch is a wallet UI that appears to complete while the dApp loses the callback, receives a stale signature, gets a rejection, or submits a transaction with a different chain effect.
- **Gate passed for a scoped prototype.** The team has a current signed target and a real callback lifecycle problem. An operator can run a pinned wallet scenario against a disposable Android device and test validator. A single report can tie the exact APK and run window to structured app evidence and an independent finalized chain check. Few components are individually difficult to reproduce. The candidate advantage is a maintained compatibility and regression suite that developers can use without building and operating it.
- **Gate failed for the broad platform.** Phone Harness plus Codex plus the Solana CLI already delivers interactive control, UI debugging and wallet environment setup. A broad device cloud, proprietary AI, general MCP frontend, decentralized supply and a token would add cost without a validated edge. Paid demand and supply remain hypotheses.
- **Why pay.** Charge per release or per team for retained reports, maintained wallet/provider cases and optional attended Seeker verification. Early validation is three Solana Android teams running their own builds, two repeat CI uses, and at least one paid pilot or written purchase commitment after comparing with internal scripts. These are future criteria.
- **Solana Mobile value.** Earlier detection of wallet handoff and settlement regressions, lower effort to reproduce compatibility issues, and explicit evidence for hardware-only tests. Ask ecosystem partners whether they would accept these reports as release evidence. Publication and approval remain official dApp Store steps.
- **Minimum demo.** Show the existing APK as a target where possible. Run a native fixture with the official test wallet, expose callback and receipt through MCP, and demonstrate a generated signature without broadcast failing the chain gate. Then rerun and show finalized transfer and screenshots. Show provider settlement only as a clearly isolated local token demonstration.
- **Expansion.** Candidate APK compatibility matrix, CI checks, second wallet adapters, attended partner hardware, optional diagnosis using the customer's MCP client and typed exports. Hiring testers and paying them in USDC only add value after job supply and acceptance are established. SKR has no initial economic purpose.
- **Commercial and technical blockers.** No independent customer interviews, no verified rentable Seeker stock, no hardware acceptance, no hosted isolation or APK-malware containment, no audit of payment operations across tenants and no proof of enough recurring demand. An attended Seeker partner and one real release builder are the next discriminating experiments.
